# Sandbox email sink key mapping

This stage adds only two ExternalSecrets in `rbx-commerce-sandbox`. It does not create a sink pod, expose a Service, route Commerce, or set Secret values. Both read the existing source `rbx-ia-br/rbx-commerce-sandbox-secrets` through the namespace's `kubernetes-store`. The service key becomes `satwake-email-sink-service-key/SATWAKE_EMAIL_SINK_SERVICE_KEY`; the separate operator key becomes `satwake-email-sink-operator-key/SATWAKE_EMAIL_SINK_OPERATOR_KEY`.

Before merging, the fail-closed sandbox Comms URL change in [Infra #306](https://github.com/rbxrobotica/rbx-infra/pull/306) must be deployed and verified in the running Commerce pod. Its inert URL is a permanent rehearsal invariant. In a separately approved source Secret operation, generate two unrelated sandbox-only keys of at least 32 bytes and store them durably as `COMMS_SERVICE_API_KEY` and `SATWAKE_EMAIL_SINK_OPERATOR_KEY`. Do not copy the production Comms key or print either value. The normal Ansible patch in Infra #301 preserves extra properties, but source Secret recreation still requires re-provisioning these keys.

Because Argo auto-syncs this overlay, merging this stage requires approval for the ExternalSecret reconciliation. After sync, confirm both ExternalSecrets report Ready and both target Secrets contain their expected **key names** only. A missing source property makes an ExternalSecret unready; stop before deploying the sink workload. The operator key must not be copied into the Commerce runtime Secret or pod. The following workload stage may be deployed only after these checks pass.
