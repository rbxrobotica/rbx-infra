# Satwake sandbox checkout email sink

This overlay runs the [Comms sandbox email sink](https://github.com/rbxrobotica/rbx-comms/blob/main/docs/ops/satwake-sandbox-email-sink.md) inside `rbx-commerce-sandbox`. It accepts the checkout email-code request and holds the code in memory for a single operator claim. It does not send email, persist codes, or prove mailbox delivery. Production Comms, Postmark, and Meta are outside this path.

## Reconciliation gates

`rbx-commerce-sandbox` is an Argo CD Application with automated sync. Merging this overlay deploys the new sink and changes the sandbox Commerce `COMMS_API_URL`; therefore keep the PR in draft until the operator has approved this exact deployment and all gates below are met.

1. Confirm the Comms image tagged `sha-752b3db` was built successfully from merged Comms #22 and contains `/satwake-email-sink`. Confirm the image can be pulled by the sandbox namespace. The production Comms image is unchanged.
2. In the durable sandbox credential store, generate two **different** random values of at least 32 bytes. Place them in source Secret `rbx-ia-br/rbx-commerce-sandbox-secrets` as `COMMS_SERVICE_API_KEY` and `SATWAKE_EMAIL_SINK_OPERATOR_KEY`. Do not copy a production Comms service key. Prepare the Secret before merge and verify **key presence only**, not values. If the source Secret is recreated, these properties must be restored before any rollout. Infra #301 preserves additional properties during the normal Ansible update, but a new source Secret still needs both keys populated.
3. Infra #282 must map `COMMS_SERVICE_API_KEY` into sandbox Commerce as a mandatory env reference. This overlay maps that same source property into a **separate** sink service-key Secret, and maps `SATWAKE_EMAIL_SINK_OPERATOR_KEY` into a distinct operator-key Secret used only by the sink. Wait for both ExternalSecrets to be Ready before rolling pods. Missing source properties prevent the sink pod from starting; merging #282 without its source properties can also block the Commerce pod.
4. Complete the sandbox Commerce migration and isolated tenant preflight in [Infra #282](https://github.com/rbxrobotica/rbx-infra/pull/282) before promoting the Satwake Commerce image or using checkout. Confirm the sandbox uses `ASAAS_ENV=sandbox`. Keep `SATWAKE_EMAIL_VERIFICATION_REQUIRED` unset until the sink, source keys, checkout route, and UI are ready to test together. The sandbox Asaas webhook remains a separate provider gate.
5. Review the rendered manifests and obtain explicit approval for the Argo deployment. The sink must have exactly one replica, no inherited provider/database variables, no Ingress, no Service port 8081, and a NetworkPolicy allowing dispatch only from sandbox Commerce with no egress. The operator claim listener binds to pod loopback; access requires authorized `kubectl port-forward` and the separate operator key.

The Commerce sandbox Deployment sets `COMMS_API_URL` directly to `http://satwake-email-sink.rbx-commerce-sandbox.svc.cluster.local`. Its legacy source Secret may still contain a production Comms URL, but the pod no longer reads that property. Check the effective Deployment environment before issuing any code. If the sink is unavailable, challenge dispatch fails against this internal URL; do not redirect it to production Comms to make a test pass.

## Verification after an approved deploy

Inspect the effective Commerce environment **without printing any Secret values**, both ExternalSecret Ready conditions, sink readiness, Service ports, and the NetworkPolicy. Use only reserved addresses such as `buyer@example.invalid`. A request without the service key must return 401, a valid dispatch must return 202, one authorized operator claim must return a six-digit code, and a second claim must return 404. A wrong operator key must return 401 without consuming the code. Follow the Comms runbook for a loopback-only claim procedure; never record the code or keys in CI logs, tickets, or shell history. Finally test wrong-code and expired-code rejection through the sandbox checkout UI. These checks prove only the isolated challenge flow, not real email delivery.

If the sink rollout fails, suspend the sandbox checkout surface and correct the missing source keys or image before retrying. A blind revert of this overlay restores the old production Comms URL from the sandbox source Secret; do not send sandbox challenges during that state. Keep paid media and production buyer journeys off until the separate end-to-end release gates are satisfied.
